    QScheduler Instances

    A QScheduler instance (quantum task scheduler) can be shared by several HEAppE instances. Assign a HEAppE instance to let it reach the QScheduler and, optionally, receive task and session notifications through its own QScheduler notifier. QScheduler features require HEAppE 6.6.0 or newer; older HEAppE instances cannot be assigned. Quantum machines are added per HEAppE instance on the Clusters page.

    QScheduler 0.2.1+: admin API inside the container (its ADMIN_TOKEN); older: docker exec <container> qscheduler ... and docker restart.
    The container must run an SSH server. Commands run as qscheduler ... inside it.
    {% include 'partials/qscheduler_sshc_warning.html' %}
    The server's host key is pinned on registration and checked on every later connection.
    Before QScheduler 0.2.1, new machines and notifiers need a service restart (0.2.1+ is managed over its admin API, no restart). The default sends SIGTERM to PID 1 (graceful shutdown) and relies on the container's restart policy. Leave it empty to restart manually (the instance is then marked "restart pending").
    QScheduler 0.2.1+ is managed only over its admin API. Leave empty to take it from the container environment; when another HEAppE Management already manages this QScheduler, copy it from there (Actions → Admin token... → Show).
    Update QScheduler Instance
    Recreates the container with the same configuration (database, networks, ports); for git the image is rebuilt on the instance's Docker host. Machines, notifiers and projects are kept in PostgreSQL. If the new version is not healthy, the previous container is restored. Downgrades are refused (database migrations are one-way). Updating to 0.3.0 backs the database up first and restores it on failure; machines then accept tasks of at most 15 minutes unless their max task time limit is raised (checked against the queues afterwards).

    For a QScheduler on this Docker host, its container joins the HEAppE API network (the HEAppE API restarts briefly). A remote QScheduler must be reachable from HEAppE at its configured host and port.
    Every cluster of this HEAppE on this QScheduler gets its own notifier <identifier>.<machine> with its own token, created when the cluster is added on the Clusters page.     Log level of

    Reading the current level...

    A RUST_LOG filter: a default level and per-module levels, e.g. info,qscheduler=debug,hyper=warn.
    QScheduler reads the log level only at startup, so the container is recreated with the same image and settings. Requests fail for a few seconds; running work is persisted and re-attached. On failure the previous container is restored. Use debug or trace only temporarily: they log a lot.
    Service limits of

    Empty: QScheduler's default (shown as placeholder). Active items are unfinished tasks plus open sessions of a user; QScheduler answers 429 over a limit and 413 for a payload larger than the limit.
    QScheduler reads these only at startup: the container is recreated with the same image and settings. Requests fail for a few seconds; running work is persisted and re-attached. On failure the previous container is restored.
    Project prefix:

    HEAppE 6.7.0+ names its QScheduler projects and users <prefix>.<name>, so several HEAppE instances can share one QScheduler. The prefix comes from the cluster setting QSchedulerProjectPrefix; without it HEAppE falls back to the notifier name, which contains a dot, and refuses to submit. You can choose the prefix until the first migration; after that it never changes.

    Reading HEAppE and QScheduler...
    Users of

    Creates the internal network with its own subnet and connects QScheduler there with a static address (and its aliases). Then:

    • the heappe container of every assigned HEAppE instance joins it (live, and in its docker-compose.override.yml) and must reach QScheduler there;
    • only then QScheduler leaves the HEAppE networks. No downtime; the clusters keep their host name.
    • On failure everything is rolled back and nothing else changes.
    Internal network <name>_qs_net: QScheduler gets the static address .2, the assigned HEAppE containers join it. The subnet is proposed from QSCHEDULER_NETWORK_POOL; change it if it collides with your LAN or VPN.

    Host names HEAppE clusters can use instead of the container name{% if alias_zone %}, inside {{ alias_zone }}{% endif %}; unique on this host, one cluster per alias.

    • Applied as Docker network aliases on : QScheduler is reconnected to it, which interrupts it for well under a second for the HEAppE instances on that network.
    • An alias that a HEAppE cluster still uses cannot be removed.

    Remote instance: the aliases are only stored. Add each with the QScheduler's IP as an extra host of the HEAppE instance (Containers & Services > Extra Hosts); to be automated.

    One per line or comma separated; empty removes all.
